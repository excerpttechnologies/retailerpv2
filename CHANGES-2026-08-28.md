## 1. Delivery / LR dialog — Opened At removed, real date pickers

**Files:** `app/admin/transport/delivery/fields.js`, `components/DeliveryView.jsx`,
`components/Field.jsx`, `lib/validate.js`

- The read-only **Opened At** clock is gone. It duplicated Transaction Date,
  which is the field actually stored.
- **Transaction Date** is now a date **and time** picker, defaulting to the
  current date and time, both editable. This needed a new `datetime` field type
  in `Field.jsx` (renders `<input type="datetime-local">`) and matching handling
  in `lib/validate.js` so the value lands on the `Date` schema path.
- **Booking Date** now uses the native calendar too. Both fields previously used
  `displayFormat: 'DD/MM/YYYY'`, which renders a masked text box that has to be
  typed by hand.

Storage is unchanged — both wrote ISO dates before and after.

**Also fixed while here:** `bookingDelayDays()` measured elapsed milliseconds.
Now that Transaction Date carries a clock time and Booking Date does not, a
same-day booking would have measured ~0.9 days and rounded up to "1 day". It now
compares whole calendar days.

**Timezone note:** the stored value is UTC but `datetime-local` speaks local
time, so `Field.jsx` converts on the way in. A naive `slice(0, 16)` would have
shown the wrong clock to anyone outside UTC. Round-trip verified:
`22:45 local → stored 17:15Z → redisplays 22:45`.

## 2. Transporter quick-add was silently failing

**File:** `components/DeliveryView.jsx`

`TRANSPORTER_QUICK_FIELDS` filtered `transporterCode` out of the form, but that
field is `req: true` and `/api/transporter` validates against the whole field
list. Every submit returned **422** naming a field the dialog never rendered, so
`ModalForm` filed an error against a control that did not exist and the dialog
just sat there — no transporter, no message.

The quick-add now uses the full field list. A quick-add may drop optional fields;
it can never drop required ones.

## 3. Supplier quick-add now opens the real 3-tab form

**Files:** `components/DeliveryView.jsx`, `components/TabbedFormView.jsx`

The "+" beside Supplier Name opened a 5-field cut-down dialog. It now opens the
full **Basic Information / Purchase Details / Financial Details** form — the same
`TABS` the Contacts › Suppliers page uses — saving per tab.

`TabbedFormView` gained one optional prop:

```js
export default function TabbedFormView({ cfg, id, slug, onSaved })
```

When `onSaved` is passed, finishing the last tab calls it instead of navigating
to the list, so the dialog closes and you stay in the consignment you were
booking. Every existing caller passes nothing and is unaffected.

The dialog deliberately does **not** close on backdrop click — it is a three-tab
form and a stray click would discard everything typed.

About 40 lines of dead quick-add scaffolding were removed.

## 4. New supplier / transporter not appearing until page refresh

**Files:** `components/useOptions.js`, `app/api/options/route.js`,
`components/DeliveryView.jsx`, `components/TransactionFormView.jsx`

**Root cause:** `/api/options` returned **no `Cache-Control` header at all**.
With no cache directive the browser is free to answer a repeat GET from its own
memory cache for the life of the document. The existing `key`-remount trick did
refire the fetch — the browser simply never asked the server.

Three parts to the fix:

1. `/api/options` now sends `Cache-Control: no-store` (verified in the response
   headers). This also covers the forms that fetch `/api/options` directly rather
   than through the hook.
2. `useOptions` sends `cache: 'no-store'`.
3. New `refreshOptions(ref)` broadcast — a create tells every mounted dropdown for
   that ref to reload, instead of relying on React remounting a control.

Wired into the Delivery transporter and supplier buttons, and into
`TransactionFormView`'s quick-adds, which had the same latent problem on the GRC
and purchase screens.

Because `TabbedFormView` only reports back on the last tab but the supplier is
created on the first, closing the supplier dialog early also refreshes.

## 5. Vendor GST No was always blank on the GRC add screen

**Files:** `app/admin/transaction/purchase/grc/form.js`,
`components/TransactionFormView.jsx`

`vendorGstNo` was declared `readOnly` but **nothing ever wrote a value into it**.
Selecting a Vendor only set `supplierId`; the GST box had no source at all.

The Vendor field now declares where to pull from:

```js
"fillFrom": { "endpoint": "/api/supplier", "map": { "vendorGstNo": "gstNo" } }
```

`TransactionFormView` honours `fillFrom`: when such a field changes it fetches
that record and copies the mapped values in. Clearing the Vendor clears the GST
box; a vendor with no GST recorded yields an empty box; a race guard stops a slow
response for a previous vendor landing on top of the current one.

`fillFrom` is opt-in, so no other screen changed behaviour.

## 6. Barcode Item image now read from `barcodeLabel`

**Files:** `lib/barcodeLabel.js`, `app/api/inventory-barcode-list/route.js`

The mobile app now writes the photo straight onto the barcode row rather than
into a separate `productImage` collection. Confirmed in the database — 5 of 69
`barcodeLabel` rows carry `imageUrl`, `filePath`, `mimeType`, `originalName`.

- Those four fields are now declared on the `barcodeLabel` schema. They were
  arriving only because the route uses `.lean()`; declaring them makes them
  first-class and safe under a non-lean read or a `.select()`.
- The route reads `productImageUrl: r.imageUrl || ''` straight off the row. The
  `ProductImage` import, the barcode-value collection, the lookup map and the
  whole `ProductImage.find()` query are removed — one fewer collection hit per
  request.

**Consequence to be aware of:** 7 older photos lived only in `productImage` and
no longer appear (`pr0124su`, `pr0126su`, `18A1000` and others). This was the
intended clean cut. Re-uploading from the mobile app puts them on the barcode row.

## Verification

- Every changed file parse-checked with Next's bundled Babel.
- `next build` reported **Compiled successfully**, 221/221 pages, for the changes
  up to and including item 5.
- Item 6 tested over real HTTP against the live database:

```
unauthenticated                 -> HTTP 401   (still gated)
authenticated, location ...02b0 ->  5 rows,  1 with image
authenticated, location ...02dc -> 56 rows,  4 with image
search=18A100                   -> 19 rows, GRC numbers joined, 3 with image
```

Rows without a photo return `productImageUrl: ""`, so the list's image column
renders its placeholder rather than breaking.

## Known issues NOT introduced by these changes

- **Image URLs mostly do not load.** Four of the five point at
  `http://192.168.31.25:4000` — a LAN address. The fifth is on
  `wovenessencemobile.etpl.ai`, which answers at the root (301) but not on
  `/uploads/itemsbarcodeimage/...`. The API returns whatever the mobile app
  stored; making these resolve is a mobile-backend change.
- `app/api/barcodeitem/route.js` still joins `ProductImage`. Left untouched.

## Note for whoever edits these files next

Several files in this project keep a large commented-out previous version above
the live code — `lib/validate.js`, `components/Field.jsx`, `components/ListView.jsx`,
`app/api/options/route.js` and others. A search-and-replace will hit the dead copy
first. Always confirm you are editing the **second** block.

`app/api/inventory-barcode-list/route.js` uses **CRLF** line endings while most of
the project uses LF. Tooling that assumes LF will fail to match in that file.
